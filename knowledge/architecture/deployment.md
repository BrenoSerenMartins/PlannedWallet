# Production deployment

`./deploy.sh` is the main-to-Render release workflow, run in Bash with Node 24, git, gh and curl. Shell files use LF line endings. `npm run deploy` remains the existing local production server preparation/start command; it does not publish to Render.

1. Run `./deploy.sh --prepare`. It pulls `origin main` with fast-forward only and writes an ignored `.verification/deploy.*/review.txt` report. Read relevant knowledge notes and inspect upstream changes and the complete release diff for duplicate or contradictory behavior. If main diverges or a merge conflicts, the agent integrates it deliberately, resolves conflicts, reviews and repeats preparation; no automatic ours/theirs selection or force push.
2. Update relevant knowledge notes and explicitly stage reviewed source and documentation with `git add <paths>`. Include knowledge in every release commit. Never stage private source documents or credentials. Preparation does not manufacture documentation or silently stash changes.
3. Run `./deploy.sh "Commit message" --reviewed=<full origin/main SHA>`. This attests to the agent's semantic review of that base, not an automated guarantee. Upstream advancement invalidates the attestation; repeat preparation and review. Dirty unstaged/untracked files block the release.
4. The script installs locked dependencies, checks API contracts, lint, types, architecture boundaries, unit tests, build, secrets and browser tests, reusing the existing quiet verification runner for shared checks. The browser suite uses two isolated workers and stops at its first failure, with a 90-second per-test limit for multi-route responsive scenarios; assertion timeouts remain unchanged. Every step prints one OK line; failures stop with a private log path. The npm cache defaults to ignored `.verification/npm-cache` unless configured by the caller. Dependencies require npm/network, and Playwright requires an installed browser (optionally `PLAYWRIGHT_EXECUTABLE_PATH`).
5. Identify the most recent successful Render production deployment through GitHub and require healthy `/health` and `/ready` responses. Compare the release's SQL files and migration runner to that exact commit, not to `origin/main`. If both are byte-identical, report that this release needs no schema changes; no database connection is required. If the baseline cannot be identified or there is any migration/runner difference, run `npm run db:migrate` using administrative `DATABASE_URL` in ignored `.env.local`. The existing runner uses validated TLS, the repository SQL ledger and an advisory lock; applied versions are skipped. A migration failure always blocks push. This does not claim every historical ledger entry was independently audited during an unchanged-schema release. SQL must remain compatible with the application already running until code is published. Review locking/backfill impact; schema changes are not automatically rolled back if a later stage fails.
6. Commit only staged changes, push main without force, and wait for the GitHub deployment status for the exact pushed SHA in Render's `main - plannedwallet-pilot` environment. Then require HTTP 200 from `/health` and `/ready`. This requires `curl`, authenticated `git` and `gh`, Render auto-deploy and deployment status integration. A timeout, failed/superseded deployment or failing health is not a completed deployment.

Logs are under ignored `.verification/`, created with restricted permissions. The script never prints raw command output, which may contain credentials. It does not rotate database credentials or alter hosting configuration. After failure, fix the cause and repeat the reviewed workflow; applied migrations are not replayed. A push rejection requires integration and checks again. If push succeeded but observing Render failed, inspect/retry `node scripts/verify-production.mjs <pushed SHA>` without making an artificial new commit.

Authentication: use `gh auth login --hostname github.com --web`, then `gh auth setup-git`. Database migration authentication uses the supplied administrative PostgreSQL connection, not Supabase CLI login. If this machine cannot reach PostgreSQL, run `npm run db:migrate` from a trusted machine with this repository/current main, dependencies and its own ignored `.env.local`; a release requiring schema changes remains blocked here until it can verify the migration step. Never bypass a required stage or weaken TLS to make the script say OK.

The upstream changes reviewed when introducing this workflow already included `deploy.sh`, card artwork/deletion and ledger daily totals migrations. The workflow extends that script rather than introducing a second publisher. No schema or financial behavior changes are part of this automation update.

Release checks also retain confirmed invoice routing when the same source is offered for another month: return the existing confirmed source without moving its cycle or creating entries. Responsive smoke checks target the dashboard's visible balance region and the unified upload action rather than retired headings and destination controls.

Browser regression fixtures follow the current main UI: collapsed planning groups, supported Banco do Brasil accounts and concise identity/category learning toggles. Tests continue to assert financial totals, explicit learning intent, sequential uploads, pause/unmount behavior and duplicate-safe source routing. Run separate Playwright commands sequentially, or isolate both the output folder and server lifecycle; otherwise one runner can delete another runner’s traces or stop its reused server.
